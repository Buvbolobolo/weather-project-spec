ОБЩЕЕ ОПИСАНИЕ ПРОЕКТА

Название проекта: WeatherApp

Тип продукта: Progressive Web Application (PWA) / Веб-сервис

Цель: Разрабатываемый проект будет представлять собой веб-сервис анализа погоды, позволяющий получать пользователям актуальные погодные данные, прогнозы, погодные карты и персональные уведомления (алерты)

Основные источники данных:  Open-Meteo Forecast API, Open-Meteo Geocoding API, Nominatim Reverse Geocoding.

Ключевое отличие: Фокус на координатах (геоточках), а не только на городах, что позволяет получать точные данные для любого места.

3. АНАЛИЗ ПОЛЬЗОВАТЕЛЕЙ (ГРУППЫ)
================================================================================

ГРУППА 1: Городские жители (Urban Residents)

Описание: Люди, которые живут в городе и используют сервис для повседневного планирования. Сюда же входят люди с активным образом жизни (велосипедисты, бегуны, курьеры).
Контекст: Ежедневно, утром перед выходом из дома или в течение дня.
Потребности: Быстро узнать погоду в своём районе или конкретной точке (парк, стадион, офис). Получить уведомление, если погода ухудшится во время прогулки/тренировки.
Ключевые функции: Текущая погода, почасовой прогноз на 24 часа, сохранение точек на карте, базовые алерты (дождь, ветер).

ГРУППА 2: Планировщики поездок (Travel Planners)
Описание: Люди, которые планируют отпуск, командировку или путешествие в другой город/регион и хотят знать погоду заранее.
Контекст: Периодически, перед поездкой (за несколько дней или недель).
Потребности: Увидеть прогноз на 5-10 дней вперёд. Сравнить погоду в нескольких точках маршрута. Понимать общие тенденции (будет ли тепло, будут ли дожди в дни поездки).
Ключевые функции: Прогноз на 5+ дней, сохранение нескольких локаций (маршрут), визуализация температурных трендов.

ГРУППА 3: Метеозависимые пользователи (Weather-Dependent Users)
Описание: Люди, чья деятельность или самочувствие сильно зависят от погодных условий (аллергики, люди с хроническими заболеваниями, организаторы мероприятий, фермеры).
Контекст: Постоянно, несколько раз в день, требуют детального контроля.
Потребности: Максимально подробная информация (давление, влажность, УФ-индекс, качество воздуха). Гибкая настройка алертов под конкретные пороги значений.
Ключевые функции: Расширенные метрики, кастомные алерты (любой параметр + любой порог), история изменений погоды.

5. ПОЛЬЗОВАТЕЛЬСКИЕ СЦЕНАРИИ (USER JOURNEYS)
================================================================================

СЦЕНАРИЙ 1: Первое использование и добавление в измбранное
Пользователь открывает сайт.
Приложение проверяет localStorage. Если есть сохраненные данные — загружает их. Если нет — предлагает выбрать город.
Пользователь переходит к карте или использует поиск.
Вводит название города или кликает на точку карты.
Frontend отправляет запрос на Backend: GET /api/weather/by-coordinates?latitude=...&longitude=...
Backend запрашивает данные у Open-Meteo, кэширует ответ (TTL 300 сек) и возвращает нормализованные данные.
Frontend отображает погоду, почасовой и дневной прогноз.
Пользователь нажимает «Добавить в Избранное».
Данные сохраняются в localStorage (ключ: weather-favorites). Дубликаты предотвращаются.

СЦЕНАРИЙ 2: Настройка и получение Push-уведомления («Прогноз на завтра»)
Пользователь выбирает город из списка или на карте.
В блоке «Погодная сводка» нажимает кнопку «Включить уведомления на завтра».
Если разрешение браузера не выдано — запрашивается разрешение (Notification API).
Frontend генерирует подписку Push (Subscription Object) и отправляет её на Backend вместе с данными алерта.
Endpoint: POST /api/push/register-alert.
Backend сохраняет подписку и настройки алерта в файл push_store.json.
Запускается фоновый цикл (asyncio loop), который раз в интервал (напр., 10 мин) проверяет условия.
При совпадении времени отправки Backend формирует сообщение («Завтра в Москве дождь...») и отправляет Web Push через VAPID.
Пользователь получает системное уведомление ОС, даже если вкладка браузера закрыта.
Backend обновляет поле last_notified_on, чтобы не слать дубли в тот же день.

СЦЕНАРИЙ 3: Работа с картой и поиск
Пользователь видит интерактивную карту (Openstreetmap).
Вводит название города в поле поиска.
Frontend вызывает геокодинг (через Backend или напрямую Open-Meteo Geocoding).
Карта центрируется на найденном городе, ставится маркер.
Автоматически подгружается погода для этой точки.
Пользователь может переместить маркер вручную или кликнуть в другое место — данные обновятся реактивно.

СЦЕНАРИЙ 4: Переключение темы интерфейса
Пользователь нажимает кнопку переключения темы (светлая/тёмная).
Выбранная тема сохраняется в localStorage (ключ: weather-theme).
При следующей загрузке страницы тема восстанавливается автоматически.

6. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
================================================================================

FRONTEND (Клиентская часть)
Технологии: React 19 + TypeScript, Axios, Openstreetmap + React-Leaflet, CSS (кастомная адаптивная дизайн-система)

1. Главный экран (Dashboard)
- Отображение текущей температуры (фактической и «по ощущениям»)
- Крупная иконка погодных условий
- Блок «Детали»: Влажность (%), Давление (мм рт. ст.), Ветер (м/с), Видимость (м).
- Кнопки быстрой навигации: «Перейти к прогнозам», «Перейти к карте», «Перейти в начало»
- Кнопка переключения светлой/тёмной темы

2. Почасовой прогноз
- Горизонтальный скролл-лист на 24 часа
- Данные: Время, Температура, Иконка, Вероятность осадков , Ветер
- Формируется начиная с актуального часа точки
- Адаптация под мобильные экраны (горизонтальный скролл при нехватке ширины)

3. Прогноз на 7 дней
- Горизонтальный список по дням
- Данные: Дата, Мин/Макс температура, Основная погода дня, Ветер
- Технически строится на 8 днях для полного недельного цикла по дням недели
- Визуально подается как блок «Ближайшие 7 дней»

4. Интерактивная карта
- Библиотека: Openstreetmap
- Возможность выбора точки кликом на карте
- Поиск города по названию в поле ввода
- Отображение текущей выбранной точки маркером
- Кнопка «Добавить в Избранное» для текущей точки

5. Избранное (Сохранённые локации)
- Список сохранённых точек пользователя
- Быстрый выбор сохранённых точек из списка
- Возможность удаления точки из Избранного
- Дедупликация по нормализованному идентификатору координат
- Защита от повторного добавления одной и той же точки
- Восстановление списка при загрузке страницы

6. Система уведомлений (Алерты):
- Триггер: Кнопка «Включить/Выключить уведомления на завтра».
- Визуализация: Кнопка меняет цвет (Синий/Серый) в зависимости от статуса.
- Технология: Notification API (браузер) + Web Push Protocol (сервер).
- Логика отображения:
Если вкладка активна: Toast-уведомление внутри UI (правый нижний угол, 15 сек).
Если вкладка неактивна/закрыта: Системное Push-уведомление ОС.
- Защита от спама: Флаг last_notified_on хранит дату последней отправки. Повторная отправка в тот же день блокируется.

7. PWA функции:
- Service Worker для кэширования статических ресурсов
- Offline режим: отображение последних закешированных данных
- Адаптация под мобильные экраны
- Режим минимизации: пользователь видит только значимые метрики

8. Хранение данных на клиенте (localStorage):
- weather-favorites — список избранных городов/точек
- weather-tomorrow-alerts — список активных алертов (id, label, country, latitude, longitude, last_notified_on)
- weather-last-selection — последняя выбранная точка и режим выбора
- weather-theme — сохранённая тема интерфейса


BACKEND (Серверная часть)
Технологии: FastAPI (Python), Pydantic (контракты API), Uvicorn (ASGI-сервер), pywebpush.

1. API Шлюз (Proxy)
- Сервер выступает посредником между Frontend и внешними API провайдерами
- Скрытие ключей и деталей внешних сервисов от клиента
- Rate Limiting для защиты от злоупотреблений (в production)

2. Кеширование данных
- Встроенный TTL-кэш в памяти процесса
- Время жизни кэша по умолчанию: 300 секунд (5 минут)
- Ключ кэша формируется из: координаты + тип данных + время
- Снижает нагрузку на внешние API и ускоряет ответы

3. Обработка и нормализация данных
- Нормализация координат и валидация диапазонов широты/долготы
- Преобразование кодов погоды в читаемые состояния
- Конвертация единиц измерения:
hPa → мм рт. ст. (атмосферное давление)
км/ч → м/с (скорость ветра)
- Округление температур «в большую сторону» (ceil), согласно требованиям продукта

4. Внешние источники данных
- Open-Meteo Forecast API: фактическая погода, почасовые и дневные прогнозы
- Open-Meteo Geocoding API: поиск города по названию
- Nominatim Reverse Geocoding: определение населённого пункта по координатам

5. Система Push-уведомлений
- Протокол: Web Push (VAPID).
- Хранение подписок: Файл push_store.json (структура: subscriptions, alerts).
- Фоновая задача: asyncio loop, запускаемый при старте приложения.
- Интервал проверки: Настраиваемый (по умолчанию 600 сек).

- Логика отправки:
Проверка флага активации (send_not_before_ts).
Проверка даты последней отправки (last_notified_on).
Генерация текста уведомления на основе прогноза на «завтра» (индекс 1 в массиве daily).
Отправка через библиотеку pywebpush.
Обработка ошибок подписки (удаление невалидных эндпоинтов).

6. Основные API-эндпоинты Backend:
- GET /api/health
Проверка доступности сервиса

- GET /api/push/public-key
Возвращает публичный VAPID ключ для фронтенда.

- POST /api/push/register-alert
Регистрация подписки и создание алерта.

- POST /api/push/unregister-alert
Удаление алерта.

- POST /api/push/test
Ручной триггер тестового уведомления.

- GET /api/cities
Сводка по преднастроенным городам каталога

- GET /api/weather?city=…
Погода по названию города

- GET /api/weather/by-coordinates?latitude=...\&longitude=…
Погода по точке на карте

- GET /api/overview
Данные для блока «Погодная сводка»

7. Архитектура решения

Разделение на 2 самостоятельных слоя:
- weather-project-frontend: пользовательский интерфейс и клиентская логика
- weather-project-backend: API-шлюз, агрегация/нормализация/кэширование данных

Схема потока данных:
Пользователь → Frontend (React) → Backend (FastAPI) → Open-Meteo / Nominatim → Backend → Frontend → UI
